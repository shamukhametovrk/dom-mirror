# Архитектура dom-mirror

## Поток данных

```
Xvfb ─► Google Chrome (обычный, с окном, постоянный профиль)
             ▲ CDP 127.0.0.1:9222
             │
        src/main.js ──WS /ws──► public/js (rrweb Replayer + прозрачный overlay)
             │                         │
             └──── /r?u=… прокси ◄─────┘
```

1. В страницу внедряется агент (`src/agent/`): rrweb записывает DOM, агент складывает события в очередь.
2. Сервер каждые 20 мс забирает очередь (`browser/world.js`), переписывает ссылки на ресурсы
   (`resources/rewrite.js`) и рассылает события клиентам (`mirror/hub.js`).
3. Клиент собирает копию через rrweb Replayer. Мышь и клавиатура уходят на сервер
   (`shared/protocol.js` → `http/ws.js` → `mirror/commands.js` → `browser/input-dispatcher.js`).
4. Картинки, шрифты и стили клиент берёт у прокси `/r`, а прокси — у самого Chrome.

## Слои

| Каталог | Ответственность | Зависит от |
|---|---|---|
| `shared/` | Протокол клиент ↔ сервер: типы, проверка входящих сообщений, константы rrweb | — |
| `src/cdp/` | Транспорт CDP и сессия вкладки (события уже отфильтрованы по `sessionId`) | `ws` |
| `src/agent/` | Код, который выполняется в странице, в изолированном мире | глобальный `rrweb` |
| `src/browser/` | Вкладки сайтов, изолированный мир, ввод, файлы, буфер обмена | `cdp`, `agent` |
| `src/resources/` | Учёт загрузок Chrome, стратегии получения ресурса, переписывание ссылок | `cdp`, `shared` |
| `src/mirror/` | Состояние копии, рассылка, маршрутизация команд клиента | `browser`, `resources` |
| `src/http/` | Роутер-таблица, статика, прокси, отладка, WebSocket | `mirror`, `resources` |
| `src/main.js` | Единственное место, где модули создаются и связываются | всё |
| `public/js/` | Клиент: соединение, плеер, мышь, клавиатура, каретка, файлы, панель | `shared` |

Модули общаются через явные зависимости (фабрики `createX({ ... })`) и шину событий в `main.js`:

| Событие шины | Кто шлёт | Кто слушает |
|---|---|---|
| `document` | `tab` — новый документ в главном фрейме | `world` (сброс контекста), `tracker` (сброс загрузок), рассылка URL |
| `url` | `tab` — смена адреса без перезагрузки | рассылка URL |
| `fatal` | `tab`, `cdp` — вкладка или Chrome закрылись | `main` — выход, контейнер перезапустится |

## Почему так

**Без Playwright и без `Runtime.enable`.** Playwright включает домен Runtime и держит свои скрипты во вкладке,
а это заметно антибот-скриптам. Поэтому событий из страницы нет, и сервер сам забирает очередь агента.

**Изолированный мир.** rrweb и очередь живут в отдельном JS-контексте над теми же DOM-узлами: страница не видит
`window.rrweb` и подменённых прототипов. Цена: rrweb не видит правил, которые страница добавляет через
`insertRule` после загрузки, и значений полей, выставленных скриптом без события.

**Агент — отдельные файлы.** Они проходят линтер и проверку типов. `browser/agent-source.js` склеивает их
с rrweb в один скрипт: убирает однострочные `import` и слово `export`. Поэтому в агенте импорты только
однострочные, а имена верхнего уровня не повторяются между файлами. Тест `agent-source.test.js` это проверяет.

**Правка rrweb** (`browser/agent-source.js`, `patchRrweb`). rrweb выбрасывает новый узел, если его соседа справа
нет в своей таблице, и дальше теряет все узлы, вставленные перед ним: в ChatGPT из-за этого не появлялись сообщения.
При сборке агента такой сосед пропускается так же, как исключённый из записи. Если после обновления rrweb место
правки не найдётся, сервер не запустится, а тест упадёт. Ошибки самой записи агент пишет в лог (`agent:`).

**Тема как у клиента.** Копия берёт `prefers-color-scheme` у браузера пользователя, поэтому активная вкладка на
сервере включает ту же тему (`Emulation.setEmulatedMedia`). Иначе на тёмной системе получался тёмный текст на
чёрном фоне.

**Ресурсы через Chrome.** Порядок стратегий (`resources/resolvers.js`): ответ, который Chrome уже загрузил для
страницы (`Network.getResponseBody`), затем загрузка сетевым стеком Chrome (`Network.loadNetworkResource`),
и только в крайнем случае Node. Так у запросов TLS-отпечаток, cookies и Referer настоящего браузера.

**Окружение как у десктопа** (`entrypoint.sh`). WebGL включён через программный SwiftShader, часовой пояс и
языки задаются переменными `TZ` и `ACCEPT_LANGUAGES` и записываются в профиль до запуска Chrome. Локаль
`C.UTF-8` обязательна: без неё Chrome молча не принимает файлы с не-ASCII именами.

**Размер окна вместо эмуляции.** `innerWidth`/`outerWidth` остаются правдоподобными.

**Без iframe с чужих сайтов.** Их содержимое rrweb не видит; раньше они шли картинкой, но снимки экрана
мешали вводу. Для Claude, Алисы и ChatGPT это не нужно, и слой убран ради отзывчивости.

**Клавиатура.** Нажатие и отпускание приходят раздельно, с настоящими `code`/`keyCode` и временем
пользователя. Горячие клавиши на кириллице получают латинскую букву (Ctrl+С → c).

## Вкладки и сессия

Вкладки — настоящие вкладки Chrome (`browser/tabs.js`), по одной постоянной на каждый сайт из `SITES`
(`browser/sites.js`). При запуске вкладки с прошлого раза подхватываются по адресу, недостающие открываются, лишние
закрываются. Вкладку сайта закрыть нельзя; если её закрыл сам сайт, она открывается заново.

У каждой вкладки своя CDP-сессия, изолированный мир с агентом, учёт сетевых загрузок и диспетчер ввода. Копируется
только активная: сообщения агентов фоновых вкладок отбрасываются, а при переключении агент активной делает
`takeFullSnapshot` и заново сообщает фокус. Ввод, прокси ресурсов и отладка работают с активной вкладкой через
делегаты (`browser/active-tab.js`).

**Фокус клавиатуры.** У активной вкладки включена эмуляция фокуса (`Emulation.setFocusEmulationEnabled`), у фоновых
выключена. Без неё страница, у которой Chrome забрал фокус (адресная строка после открытия вкладки), не получает
нажатий: поле на сервере в фокусе, а символы не вводятся.

Окна, которые открывает сайт (`window.open`, у цели есть `openerId`), подхватываются и становятся активными; у них
сохраняется `window.opener`, поэтому работают окна входа через сторонние сервисы. Закрыли окно — активной снова
становится вкладка, из которой его открыли. Заголовки окон сверяются с Chrome раз в секунду. Окон не больше 5.

Сессия одна: новое подключение вытесняет прежнее (`mirror/hub.js`, код закрытия 4001). Вытесненный клиент сам
не переподключается, иначе два открытых устройства выбивали бы друг друга по кругу.

## Скачивание файлов

Серверный Chrome сохраняет загрузки в `$DATA_DIR/downloads` под именем guid (`Browser.setDownloadBehavior`,
`browser/downloads.js`). О начале и конце загрузки клиент узнаёт сообщением `download`, по окончании сам скачивает
файл с защищённого адреса `/download?id=<guid>` и показывает уведомление со ссылкой на случай, если браузер не дал
скачать автоматически. Отдаются только загрузки, о которых сообщил Chrome; файлы старше часа удаляются. PDF
скачиваются, а не открываются: встроенный просмотрщик Chrome в копию не переносится (настройка профиля в
`entrypoint.sh`).

## Буфер обмена и каретка

Ctrl+C и кнопки «Копировать» на сайтах пишут в буфер сервера (X11 виртуального экрана). После действий, которые
могут что-то скопировать (отпускание кнопки мыши, сочетания с Ctrl/Cmd), сервер читает его через `xclip`
(`browser/clipboard.js`) и, если содержимое изменилось, отправляет клиенту текст или PNG. Клиент кладёт его в буфер
пользователя (`public/js/clipboard.js`); если браузер не разрешил запись без клика, показывает уведомление
«нажмите, чтобы скопировать к себе». Вставка в обратную сторону — текст из события `paste` через `Input.insertText`.

Каретка по клику ставится сразу (`public/js/caret.js`): копия находит поле под курсором (`elementFromPoint`,
`caretPositionFromPoint`) и фокусирует его, не дожидаясь сервера. Сообщение сервера о фокусе потом уточняет
каретку; если его нет 700 мс (клик на сервере попал мимо поля), копия возвращается к последнему состоянию сервера.

Каретка с сервера: агент сообщает фокус и выделение — в поле ввода позиции, в редакторе (`contenteditable`) узлы и смещения
по нумерации rrweb (`agent/focus.js`). Копия ставит туда фокус и выделение, и каретку рисует сам браузер
пользователя. Локальная правка редактора в копии заблокирована (`beforeinput`, `drop`), чтобы DOM не разошёлся
с сервером.

## Прикрепление файлов

Файлы сначала загружаются на сервер (`POST /upload`, `http/upload.js`) и лежат в `$DATA_DIR/uploads/<id>/<имя>`,
чтобы сайт видел настоящее имя (`browser/uploads.js`). Клиент знает только id; путь на сервере он указать не может.

- **Кнопка на сайте.** Окно выбора файла перехватывается (`Page.setInterceptFileChooserDialog`, `browser/file-chooser.js`),
  клиент получает `fileChooser` и открывает своё окно (`showPicker`; если браузер не дал без клика —
  уведомление «Нажмите, чтобы выбрать файл»). Загруженные файлы ставятся в поле через `DOM.setFileInputFiles`.
- **Перетаскивание и Ctrl+V с файлом.** Настоящее перетаскивание `Input.dispatchDragEvent` с путями файлов: в точку
  броска или, при вставке, в середину поля с фокусом.

## Доступ и защита

| Что | Где | Как |
|---|---|---|
| Вход | `http/auth.js`, `http/password.js` | Пароль из `PASSWORD` или из `/data/password` (генерируется один раз). Сессия — подписанная метка времени в cookie (`HttpOnly`, `SameSite=Strict`); ключ выводится из пароля, поэтому смена пароля обнуляет сессии |
| Закрытые маршруты | `main.js` → `guardRoutes` | Всё (в том числе `/upload` и `/download`), кроме `/login`, `/logout`, `/health` и `/r`. Страница уводит на вход, остальное отвечает 401 |
| WebSocket | `http/ws.js` | Нужны сессия и `Origin`, совпадающий с адресом сервиса (с `TRUST_PROXY=1` — `X-Forwarded-Host`). Ping раз в 25 с, чтобы прокси не рвали соединение |
| Прокси ресурсов | `resources/signing.js` | `/r` отдаёт только адреса с HMAC-подписью, которую сервер поставил сам при переписывании копии. Секрет в памяти, после перезапуска копия переподписывается |
| Логи | `http/ws.js` | Введённый текст не пишется никогда; с `DEBUG=1` — только типы сообщений |

`/r` открыт без входа намеренно: копия живёт в sandbox-iframe с непрозрачным origin, и запросы шрифтов и стилей
из него идут без cookie. Подпись не даёт использовать его как открытый прокси.

## Плавная прокрутка

Колесо через CDP Chrome считает «точной» прокруткой: щелчок в 100 px — один прыжок за кадр. Кроме того, серверный
Chrome обрабатывает синтетическое колесо не каждый кадр, и позиции приходят через 20–70 мс. Поэтому:

- `browser/smooth-wheel.js` — сервер разбивает щелчок на шаги по кадрам с замедлением к концу. Шаги идут по таймеру,
  без ожидания подтверждения и мимо общей очереди ввода; размер шага считается по прошедшему времени.
- `public/js/scroll-smoother.js` — копия плавно догоняет последнюю позицию сервера на каждом своём кадре
  (постоянная времени 25 мс). Переходы дальше 2000 px применяются сразу.

## Правила кода

- Цикломатическая сложность ≤ 5, вложенность ≤ 2, функция ≤ 25 строк, ≤ 3 параметров — проверяет ESLint.
- Ветвления по типу сообщения или события — таблицей обработчиков, а не `switch`.
- Каждый файл начинается с `// @ts-check`; типы протокола берутся из `shared/protocol.js`.
- Комментарии объясняют только «почему», и только там, где это неочевидно.
- Чистая логика отдельно от побочных эффектов: её тестируют `node:test` без Chrome (`test/fakes.js`).

Проверка всего сразу: `npm run check`.
